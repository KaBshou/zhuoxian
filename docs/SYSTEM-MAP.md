### 2.2 关键联动点（每一条都是一个「现在不做、以后重写」的坑）

| # | 联动 | 为什么必须提前准备 | 不准备的后果 |
|---|---|---|---|
| 1 | **标签系统 → 一切** | 你的例子：`召唤浊犬` 带 法术/召唤/单体/范围/金；词缀「召唤物伤害」「法术伤害」「金属性伤害」影响它；「范围伤害」只影响 `猛扑` 不影响 `撕咬` | 每个技能单独写 if 分支，60 个辅助石 = 上千条测不完的路径 |
| 2 | **修正器统一表示** | 装备词缀、天赋、辅助石、升华、怪物词缀、地图词缀**本质是同一个东西**：给某个属性加/乘一个值，条件是按标签 | 六套加成逻辑各写一遍，改一个数值要改六处 |
| 3 | **加算 vs 乘算必须分开** | 流放之路的 `增加 30% 伤害`（加法叠加）和 `更多 30% 伤害`（乘法叠加）是**两种不同的词缀**，玩家为了凑乘算能研究几天 | 混成一个 `dmg%`，数值曲线必然崩，后期只能重做 |
| 4 | **装备存词缀实例，不存加总值** | 通货「灭灵石 = 随机删一条词缀」要求知道「这件装备上有哪 4 条词缀、各是什么等级」 | idle-grim 现在就是加总值（`affixes[a.stat] = v`），通货做不了，得整表重写 |
| 5 | **攻击 vs 法术的伤害来源不同** | 攻击 = 武器伤害 × 技能倍率（技能升级加得少）；法术 = 技能等级曲线（升级加得多且越升越陡） | 技能表结构定错，20 个技能全部重填 |
| 6 | **召唤物走同一条伤害管线** | 召唤物有自己的属性，但要吃玩家的「召唤物/法术/金属性/范围」词缀 | 召唤物单独一套伤害计算，五个职业里带召唤的那个永远对不上账 |
| 7 | **防御结算顺序固定** | 护盾 → 护甲（物理）/抗性（五行）→ 生命，护甲要边际效应 | 「我明明有 3000 护盾怎么一下死了」这类 bug 永远查不完 |
| 8 | **物等链单一来源** | 地图阶级 → 怪物等级 → 掉落物等 → 词缀池过滤。只能有一个地方算 | 三处各算一次，掉落物等和地图对不上 |
| 9 | **技能石是「物品」** | 技能石可掉落、可交易、可装孔、可被通货改造 | 技能做成「等级解锁的技能栏」，后面想改技能石系统要重做存档 |
| 10 | **伤害管线要能「离线跑一万次」** | 离线收益 = 不渲染、只跑逻辑 | 伤害计算里掺了渲染/UI/随机数，离线收益算出来和真跑对不上（idle-grim 实测差 8~16 倍） |

## 三、必须先定的三块地基（定了以后不用返工）

### 地基 1：标签表（Tag）
所有系统和玩家沟通的唯一语言。

```
技能标签：攻击 / 法术 / 召唤 / 持续伤害 / 光环
形状标签：单体 / 范围 / 投射物 / 连锁 / 近战
元素标签：金 / 木 / 水 / 火 / 土
来源标签：主动 / 辅助 / 天赋 / 装备 / 升华
```
规则：**一条词缀只能影响「带某标签」的东西**。例如 `+20% 法术伤害` 只作用于带 `法术` 标签的伤害实例。
你的 `召唤浊犬` 例子直接验证了这套设计是必要的——它一个技能里就有两个伤害实例（`撕咬` 单体 / `猛扑` 范围），标签不同。

### 地基 2：修正器（Modifier）
```
Modifier {
  作用域: 玩家 | 全局 | 某个技能 | 召唤物 | 怪物 | 地图
  属性:   伤害 | 生命 | 攻速 | 火抗 | ...
  运算:   加算(increased) | 乘算(more) | 固定值(flat)
  数值:   number
  条件:   标签[]  ← 空 = 无条件
}
```
**全游戏只有一个 `aggregate(modifiers[]) → 最终属性` 函数。**
装备词缀、天赋节点、辅助技能石、升华、怪物词缀、地图词缀全部产出这个结构，全部走这一个函数。

这是整个项目最贵的一块，也是最值得一次性做对的一块。

### 地基 3：装备词缀实例
```
Item {
  baseId, ilvl, rarity, slots[],
  affixes: AffixInstance[]   ← 不是 Partial<Record<StatKey, number>>
}
AffixInstance { affixId, tier, value }   // affixId 决定名字/标签/部位限制
```
没有这一层，通货、打造、词缀权重偏移、装备比较界面**全部做不了**。

## 五、八个隐藏陷阱（现在不知道，做到一半才发现）

### 陷阱 1：60 个辅助石 × 20 个主动石 = 不可能手写
组合数是 540 万。**辅助石必须是「纯修饰器 + 标签约束」**，由一个函数算出结果，不能每条组合写逻辑。
- 辅助石能做的事：改数值（+伤害/-范围）、加标签、减标签、加一个机制（连锁+1、投射物+1、附加火伤）
- 辅助石**不能**做的事（第一版）：完全改变技能形态。这件事只留给传奇装备，且只做 3~5 件。

### 陷阱 2：传奇「改变技能形态」是最贵的功能
idle-grim 的 `mastery.ts` 已经踩过这个坑，注释原文：

> 符文如果改技能行为（多发、改形态、附加控制），每个技能都要单独写分支，26 个技能 × N 个符文 = 上百条没人测得完的路径。

**沿用它的解法**：传奇效果实现成「少量机制原语」的组合（连锁 +1 / 投射物 +2 / 伤害转元素 / 附加一种元素），不是任意代码。

### 陷阱 3：攻击和法术的伤害曲线完全不同
- 攻击：`武器伤害 × 技能倍率`，技能升级加得少（1 级→20 级约 +40%）
- 法术：`基础伤害(等级)`，且**越升越陡**（前期收益低、后期高）

所以 `SkillDef` 第一天就要有 `damageSource: 'weapon' | 'gemLevel'`，否则 20 个技能全部重填。

### 陷阱 4：召唤物也要走同一条伤害管线
召唤物的伤害 = 召唤物自己的基础值 ×（玩家的召唤物/法术/元素/范围词缀按标签过滤）。
所以伤害函数签名必须是 `resolveDamage(攻击者, 标签集合, 基础值)`，不能是 `playerDamage()`。

### 陷阱 5：自动施放和技能石的矛盾
流放之路是手动按键的；放置游戏必须自动。20 个主动技能自动放哪个？
idle-grim 的做法是每个技能一个 `auto` 开关 + `minTargets`（范围内至少 N 个敌人才放）。
**浊仙需要升级成「优先级列表」**：玩家排一个顺序，引擎按顺序找第一个满足条件的放。这个界面本身是个新系统，你的需求里没有。

### 陷阱 6：防御结算顺序
护盾 → 护甲（只减物理）/ 抗性（只减五行）→ 生命。护甲要有边际效应（`减伤 = 护甲 / (护甲 + K×敌人等级)`）。
顺序必须写进文档并且只有一个实现，否则「为什么我死了」永远查不完。

### 陷阱 7：通货的经济学
「黄阶灵石 = 加一条词缀」这个操作**只有在词缀池足够大时才有意义**。
池子只有 40 条词缀时，玩家点几次就出想要的，通货立刻贬值。
所以**词缀池规模（200+）和通货系统是绑死的**，不能先做通货再补词缀。

### 陷阱 8：挂机 + 赌狗的矛盾
你说「挂半天一天没出货的概率也有」——这是流放之路的乐趣。
但放置游戏的乐趣是「关掉再回来一定有收获」。两个都想要，需要明确：
- 保底给什么（通货？经验？垃圾装备？）
- 「没出货」的时长上限是多少（我建议：**连续 2 小时没有任何稀有以上掉落**，就该有一个可见的进度条告诉玩家「快了」）

## 七、六条「更好的想法」（都等你拍）

### 1. 技能石当「物品」做，不要当「技能」做
技能石 = 一件能掉落的物品，有孔位、走同一套掉落/背包/显示逻辑。
**好处**：省掉一整套「技能管理界面」，玩家已经懂「装备」了，技能石只是换个栏位。
**代价**：要先把物品系统做对（词缀实例那块地基）。

### 2. 天赋树用「共享主干 + 6 个职业起点」
流放之路原版就是这个做法：一张大图，6 个职业的起点在图上不同位置，越靠近起点越偏该职业。
**好处**：一次满足你两个需求（共享天赋树 + 职业不同），而且是成熟方案。
**代价**：天赋树 UI 是个大工程（缩放、拖拽、路径高亮）。第一版可以先做成「列表 + 节点详情」，图后面补。

### 3. 五行先做 3 种
「金木水火土」5 种 × 每种都要有：抗性、穿透、词缀、怪物抗性、技能标签 → 词缀表直接 ×5/3。
**建议第一版只做 3 种**（金 / 火 / 水），架构按 5 种设计（枚举留 5 个），后期加 2 种只是填数据。
省掉的工作量大约是总工作量的 15%。

### 4. 第一版每个系统只做「一条线」，但架构按全量设计
「先做骨架，后填肉」。具体：

| 系统 | 架构支持 | 第一版实际做 |
|---|---|---|
| 职业 | 6 个 | 3 个开放，3 个显示「封印中」 |
| 主动技能石 | 20+ | 6 个 |
| 辅助技能石 | 60+ | 12 个 |
| 天赋树 | 200+ 节点图 | 60 个节点，2 个起点 |
| 词缀 | 200+ | 60 条（够通货玩） |
| 通货 | 10+ 种 | 3 种（加词缀/删词缀/重铸） |
| 怪物词缀 | 30+ | 8 条 |
| 地图 | 多阶 | 2 阶（黄阶 1~15 / 玄阶 16~30） |
| 五行 | 5 种 | 3 种 |

**这不是缩水，这是「先让循环转起来」。** 循环转起来之后，扩内容 = 填数据表，不再是写代码。

### 5. 做一个「伤害拆解面板」（强烈建议）
鼠标移到伤害数字上，显示：
```
本次伤害 1,284
  武器基础        120
  技能倍率 ×1.5   → 180
  加算(+450%)     → 990   （装备+180 天赋+200 辅助石+70）
  乘算(×1.1)      → 1089  （火系专精）
  暴击 ×1.5       → 1634
  敌人火抗 -40%   → 980
  最终            980
```
**为什么这条最重要**：流放之路类游戏最大的劝退点是「数值不透明」，玩家不知道自己为什么打不动。
这个面板同时是：① 玩家的计算器 ② 你的调试工具 ③ **最好的教学工具**（它会逼你把变量命名清楚）。

### 6. 术语表先行（一个文件，不是散落在 UI 里）
建 `src/data/glossary.ts`，所有名词从这里取：
```
hp → 气力    mp → 浊元    护盾 → 护体罡气
暴击 → 破防   攻速 → 出手速度   施法速度 → 结印速度
力量/敏捷/智力 → 体魄/灵巧/神识
```
**好处**：以后改名字只改一处；也逼你先把世界观想清楚（这也是你说的「只需要你能编辑好背景，自圆其说」）。

### 第 8 条展开（这条最重要，因为它决定你还学不学得到东西）
你的目标是「亲手做出来 + 学会」。但修正器引擎这种代码，让初学者一行行写，会卡两周，而且卡住的原因是「不知道自己写错了什么」——那不是学，是受挫。

我建议分三类：
| 代码类型 | 谁写 | 你怎么参与 |
|---|---|---|
| **样板**（配置/导入/UI 架子/渲染） | 我写 | 读懂就行 |
| **核心引擎**（修正器聚合、伤害管线、技能解析） | 我写完 + 分段讲透 | 你做「改一处看效果」的验证实验，像现在这样 |
| **业务逻辑**（掉落/战斗循环/层数/存档字段/UI 交互） | **你写** | 保持现在的模式 |

这样你仍然会亲手写项目里 40~50% 的代码，而且是最能看到效果的那部分；而最容易让人放弃的那 50% 由我兜住。

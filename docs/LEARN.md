## 第 1 步 · 环境搭建 + 主循环 + 渲染 ✅

### 目标

浏览器里出现一个画面：暗色背景、淡淡网格、一个青色方块从左往右匀速移动，走到右边缘后从左边重新出现。

### 概念

**1. 编程语言 / 引擎 / 工具链**

- **编程语言**：写给电脑看的指令格式。我们用 TypeScript（JavaScript 的加强版）。
- **引擎**：别人写好的游戏零件包（画图、碰撞、声音）。我们**不用**引擎——因为你的游戏是 2D 文字+色块风格，用引擎反而更麻烦。
- **工具链**：把代码变成能运行的东西的那套工具。我们用 Vite。

**2. 为什么用 TypeScript 而不是 JavaScript**

JavaScript 里 `let hp = 100`，如果后面手滑写成 `hp = "一百"`，它不会报错，游戏里血量就变成了字符串，等到几十行之后才崩，而且报错信息完全对不上原因。

TypeScript 会在你写这一行的时候就画红线：`类型 "string" 不能赋值给类型 "number"`。

代价是必须先编译。这就是为什么 `npm run dev` 和 `npm run build` 是分开的。

**3. Vite 是干什么的**

你的源码是多个 `.ts` 文件，浏览器不认识 TypeScript，也不认识 `import` 这种模块写法。

Vite 做两件事：
- `npm run dev`：开一个本地服务器，实时把你的 TS 转成浏览器能懂的 JS，改代码后浏览器自动刷新
- `npm run build`：把整个项目打包压缩成几个文件，放进 `dist/` 目录，可以上传到网上

**4. 主循环（Game Loop）—— 游戏和普通程序的根本区别**

普通程序：输入 → 处理 → 输出 → 结束。

游戏：**每秒重复 60 次**「处理 → 画出来」，永不结束。

每一次叫一「帧」（frame）。60 帧/秒意味着每次你只有 16.7 毫秒。这就是为什么游戏优化那么难。

**5. 固定步长（Fixed Timestep）—— 这一步最重要的概念**

这里有个新手必踩的坑，我把它单独讲清楚。

假设你写「每帧让方块右移 5 像素」。会发生什么？

- 你朋友的电脑 144Hz 屏 → 每秒 144 帧 → 方块每秒走 720 像素
- 你的电脑 60Hz → 每秒 60 帧 → 方块每秒走 300 像素

**同一个游戏，在快电脑上快 2.4 倍。** 更糟的是，游戏卡一下（掉帧），那一帧间隔变长，方块会「瞬移」一大截，可能直接穿过怪物。

解法是两层：

**第一层：基于时间，不基于帧。**
写成 `x += 速度 × dt`，其中 `速度` 是「每秒多少像素」，`dt` 是「这一帧过了多少秒」。这样快电脑帧数多但每帧 dt 小，总位移一样。

**第二层：固定步长。**
但 `dt` 还是会波动（这一帧 16ms，下一帧 19ms）。波动会导致：这次攻击判定 3.1 像素，下次 3.4 像素，累积起来会有微小差异，玩家长时间挂机后可能出现「同一个配置，别人 8 小时通，你 9 小时通」。

所以逻辑层永远按 `1/60 秒` 推进。真实时间过了 20 毫秒？跑 1 步（16.67ms），剩 3.3ms 记在账上，下次一起用。真实时间过了 50 毫秒？跑 3 步。

这就是 `src/core/loop.ts` 里那个 `acc`（累积器）在干的事。

### 代码

我建了 5 个文件。其中**配置类文件**（`package.json`、`tsconfig.json`、`vite.config.ts`、`index.html`、`style.css`）是纯样板，和游戏设计无关，你不需要背——但 `vite.config.ts` 里有一行 `base: './'` 你现在必须知道它的作用（见下方「为什么」）。

真正要理解的是这三个：

**`src/core/loop.ts` —— 主循环**

核心是这三段：

```ts
const dt = Math.min(raw, 0.1);   // 上限 0.1 秒，防切标签页回来卡死
this.acc += dt;                  // 把真实流逝的时间记在账上

let steps = 0;
while (this.acc >= this.fixedDt && steps < 8) {
  this.update(this.fixedDt);     // 账上够一步就走一步，永远走 1/60 秒
  this.acc -= this.fixedDt;
  steps += 1;
}
if (steps >= 8) this.acc = 0;    // 补不完就放弃，宁可慢一点不要卡死
```

`Math.min(raw, 0.1)` 这一行看着不起眼，但它救你的命：你切到别的标签页 30 秒再回来，浏览器会给你一个 `raw = 30`。没有这行，下面的 while 会试图补 1800 步，页面直接卡死几秒。

**`src/core/world.ts` —— 数据层**

规矩只有一条：**这个文件里不许出现任何 canvas、颜色、字体、DOM。**

它只回答「现在是什么情况」（方块在 x=100, y=250），不回答「看起来什么样」（青色、40×40）。

为什么现在就要分开：等做到「离线收益」时，你需要把玩家关掉网页的 8 小时补算一遍。如果战斗逻辑和画面搅在一起，你根本没法在没画面的情况下算战斗。现在分开，到时候只要把 `update` 调用几万次。

**`src/core/renderer.ts` —— 画面层**

只读 World，绝不修改它。

原因：如果渲染器能改数据，那「画面刷新快慢」就会影响游戏结果。玩家换台高刷屏，游戏难度就变了——这种 bug 极难查，因为在你电脑上永远复现不出来。

**`src/main.ts` —— 组装**

只干三件事：找到 canvas、造出 World 和 Renderer、把 Loop 接起来。

以后加战斗系统、掉落系统，都是在这里 new 一下塞进 update。所有「谁依赖谁」集中在这一个文件，出问题只看这里。

### 目标

浏览器里，你用 **WASD** 或 **方向键** 推着方块走。松手就停。走到画面边缘会被挡住，出不去。

### 概念

#### 1. 事件（Event）—— 浏览器不会"告诉你键盘现在什么状态"

这是新手最容易误解的一点。

你可能以为键盘是这样一个东西：`if (键盘现在按着 W) { 往上走 }`。

**不是。** 浏览器不会主动告诉你「现在按着什么」。它只会在**事情发生的那一瞬间**通知你一次：

- `keydown` —— 某个键刚被按下（只发生一次，不是按住就一直发）
- `keyup` —— 某个键刚被松开

这叫「事件」（event）。你写一个函数挂上去，浏览器有事就叫你。

#### 2. 那怎么知道「现在一直按着」？—— 自己记账

既然浏览器只通知「按下」和「松开」两个瞬间，那"现在按着没"就得你自己记。

记法是：准备一张表（`Set`），按下时把键名加进去，松开时删掉。要问"现在按着 W 吗"，查表就行。

`Set` 你可以理解成「一个不允许重复的清单」。`add` 加入，`delete` 删掉，`has` 查在不在。

这就是 `input.ts` 里 `pressed` 那个变量的作用。

#### 3. 为什么用 `e.code` 不用 `e.key`

`e.key` 是「这个键打出来是什么字符」，`e.code` 是「这个键在键盘上的哪个物理位置」。

听起来没差别，实际差很多：

- 中文输入法开着时，按 A 可能给你 `'a'` 而不是 `'A'`
- 大写锁定开着时给你 `'A'`
- 法语键盘（AZERTY）上，A 键和 Q 键的位置是换的
- 按住 Shift 时 `e.key` 会变成 `'W'`

`e.code` 永远是 `'KeyW'`，不管输入法、锁定、布局。**做游戏一律用 `e.code`。**

#### 4. 焦点丢失（blur）—— 一个必须现在处理的坑

你按住 D 往右走，这时 Alt+Tab 切到别的窗口。

浏览器**不会**给你「松开 D」的事件，因为键盘已经不属于这个页面了。于是你的表里永远留着 `'KeyD'`，你切回来时方块一路飘到右边墙上，怎么按都不停。

这种 bug 极难查，因为你自己正常玩的时候永远碰不到。

解法：监听 `blur`（窗口失去焦点）事件，把表清空。

#### 5. 斜向速度——所有游戏新手都写错过的那个 bug

假设"向右走"每帧走 5 像素，"向下走"每帧也走 5 像素。

那"右下"呢？两个方向同时加 → 横 5 像素 + 纵 5 像素 → 实际走的距离是 `√(5²+5²) ≈ 7.07` 像素。

**斜着跑比直着跑快 41%。** 玩家只要一直按着斜向，就能跑得比设计值快四成。

修法：斜向时把距离除以 `√2`（约 1.414）。这样 7.07 / 1.414 = 5，正好一致。

JavaScript 里现成的：`Math.SQRT2`。

#### 6. 夹取（clamp）—— 把数值限制在上下限之间

要让方块不跑出画面，你需要「x 不许小于 0，也不许大于 920」。

朴素写法是 `if` 判断，但容易写错方向。更好的写法：

```
Math.max(下限, Math.min(上限, 值))
```

读法：先用 `Math.min` 把值压到不超过上限，再用 `Math.max` 把值抬到不低于下限。

### 为什么这么写（后面怎么用）

**为什么 `dir` 用 -1 / 0 / 1，而不是直接传"这一帧走多少像素"？**

因为方向是「意图」，位移是「结果」。意图和结果分开，才能一个意图配不同的结果。

第 4 步做自动战斗时，玩家不用按键盘了——但方块还是要动。那时候会有一个「AI 寻路」模块，算出一个 `dir` 交给 `world.update`。**`move` 方法一行都不用改。**

如果当初 `input.ts` 直接算好像素位移传进去，第 4 步你就得重写。

**为什么 `Input` 不直接改 `World` 的坐标？**

还是那条规矩：`World` 是数据层，不碰浏览器 API。`Input` 碰键盘，`World` 算移动，`main.ts` 负责把它们接起来。

第 15 步做离线收益时，你要在「没有键盘、没有画面」的情况下跑 8 小时的战斗。到那时你会庆幸 `World` 不依赖键盘。

**为什么斜向归一化要在 `move` 里做，不在 `input.ts` 里做？**

## 附：按下键盘之后，到底发生了什么（完整链路）

> 这一节回答你问的「为什么我一按键盘方块就动，底层逻辑是什么」。
> 同时它也是一次「怎么读代码」的示范 —— 方法就是**顺着数据流走一遍**，不是从头读文件。

### 一句话答案

**键盘并没有"推"方块。**

键盘做的事只有一件：往一张清单（`Set`）里加一个名字。

真正让方块动的是**主循环**——它每秒雷打不动跑 60 次，每次都问一句「清单里现在有什么」，然后照着算。你按不按键，它都在跑。

这叫**轮询**（polling）：不是"有事叫我"，而是"我每隔一会儿来看一眼"。游戏几乎都这么做。

### 完整链路：一次按键，六个文件

下面这条链，就是「你按下 D」到「方块右移」的全部过程。**按编号顺序看，每一条都告诉你去看哪个文件的哪一行。**

```

   │
   │ ① 浏览器立刻触发一个事件（不是你调用的，是浏览器主动叫的）
   ▼
src/core/input.ts:32   window.addEventListener('keydown', (e) => { ... })
   │                   └─ this.pressed.add('KeyD')   ← 只干这一件事：清单里加一项
   │
   │   ⚠️ 到这里为止，方块一点都没动。只是清单多了一项。
   │
   │ ② 与此同时，主循环在另一个地方一直转着（每秒 60 次）
   ▼
src/core/loop.ts:79    this.update(this.fixedDt)
   │                   └─ 这个 update 就是 main.ts 里传进来的那个函数
   ▼
src/main.ts:32         (dt) => world.update(dt, input.direction())

   ▼
src/core/input.ts:69   direction(): Direction

   │                   返回 { x: 1, y: 0 }
   ▼
src/core/world.ts:64   update(dt, dir)  →  this.move(dt, dir)   （第 65 行）
   ▼
src/core/world.ts:98   const dist = this.speed * dt          ← 这一帧走多远

   │

   ▼
src/core/loop.ts:85    this.render()
```

### 三个必须理解的点

**1. 为什么"按住"能一直动？**

因为清单里的 `'KeyD'` 一直在。每帧 `direction()` 都查到它，每帧都返回 `x: 1`，每帧 `this.x` 都加一点点。60 帧就是 60 次加法。

松手时 `keyup` 把 `'KeyD'` 删掉（`input.ts:41`），下一帧查不到了，`x` 变成 0，加法变成加 0，方块停住。

**2. 为什么不会"按一下动一次"？**

因为**没有代码在响应"按键"这件事本身**。按键只是改了数据。移动完全由循环驱动。

理解了这个，你就明白为什么第 15 步的离线收益能做得出来：把循环的 `update` 调用一万次（不调用 `render`），就是"补算八小时"。方块根本不关心自己有没有被画出来。

**3. 这个结构的好处：三层可以各自换掉**

| 层 | 文件 | 只负责 | 换掉它会怎样 |
|---|---|---|---|
| 输入 | `input.ts` | 键盘 → 方向 | 换成手柄 / 触屏摇杆 / 手机虚拟按键，`world.ts` 一行不用改 |
| 逻辑 | `world.ts` | 方向 → 新坐标 | 第 4 步自动战斗：把 `direction()` 换成 AI 算的方向，其余不动 |
| 画面 | `renderer.ts` | 坐标 → 像素 | 换成像素画 / 3D，逻辑一行不用改 |

## 第 3 步 · 敌人与自动寻路 ✅

> 这一步是**第一次让"别人"动起来**。也是第一次遇到"数学上的小陷阱"。
> 代码还是那个规矩：**文件结构我给，核心那 4 行你写。**

### 目标

画面上出现**三个暗红色方块**（比你的青色方块小一点），从三个角出发，**直线**朝你走过来。

你往左跑，它们往左拐；你停下，它们贴上来。你跑到角落，它们挤成一团。

### 概念

#### 1. 方向 ≠ 距离（这一步唯一的新知识）

假设敌人在 (60, 60)，你在 (480, 270)。

它需要知道的是「往右下方走」，但你手上只有两个数：

```
dx = 你的 x − 敌人的 x = 480 − 76 = 404      ← "还差 404 像素"
dy = 你的 y − 敌人的 y = 270 − 76 = 194      ← "还差 194 像素"
```

**这两个数是"距离差"，不是"方向"。** 差得越远数越大。如果直接拿来当方向用，就会变成：

> 目标在 500 像素外 → 一帧走 500×1.5 = 750 像素（直接飞出画面）
> 目标在 5 像素外 → 一帧走 5×1.5 = 7.5 像素（走过头，来回抽搐）

所以必须先把"距离差"压成"纯方向"。

#### 2. 单位向量：把长度压成 1，方向不变

做法只有一步：**除以它自己的长度**。

```
len = √(404² + 194²) ≈ 448          ← 直线距离
404 / 448 ≈ 0.90                     ← 方向分量 x
194 / 448 ≈ 0.43                     ← 方向分量 y
```

`(0.90, 0.43)` 这个数对，长度刚好是 1，方向还是"右下"。这叫**单位向量**。

- 长度恒为 1 → 乘上任何速度，都是"朝这个方向走固定距离"
- 两个分量都在 −1 到 1 之间 → 一眼能看出朝向

然后乘上 `speed * dt`，就是这一帧该走的像素数：

```
新 x = 旧 x + 0.90 × (90 × 0.0167) = 旧 x + 1.35
新 y = 旧 y + 0.43 × (90 × 0.0167) = 旧 y + 0.65
```

每一帧都这么走，连起来就是**一条直线**。

#### 3. `Math.hypot(dx, dy)` 是什么

就是勾股定理，`√(dx² + dy²)`。浏览器内置，不用自己写。

`hypot` 是 hypotenuse（直角三角形的斜边）的缩写。你只要记住：**给两个直角边，给你斜边长度。**

> 为什么不用 `Math.sqrt(dx*dx + dy*dy)` 手写？效果一样，但 `Math.hypot` 在数值特别大或特别小时更不容易出精度问题。这是「用现成的」的好例子。

#### 4. 除以 0 会怎样（这段我替你写好了）

如果敌人正好站在你身上，`dx` 和 `dy` 都是 0，`len` 也是 0。

`404 / 0 = Infinity`，`0 / 0 = NaN`。

`NaN` 是"不是一个数"（Not a Number）。它有个可怕的特性：**任何数和它做运算，结果还是 NaN**。所以坐标一旦变成 NaN，方块就永远回不来了 —— 它不会报错，只是从画面上消失，而且你怎么改代码都没用（除非刷新）。

所以 `enemy.ts:56` 那行提前 `return` 了。**它必须写在除法前面**，写在后面就晚了。

> 这类"除以一个可能为 0 的数"，是所有语言里最常见的崩溃原因之一。你以后写任何除法，都要先问一句："这个除数有没有可能是 0？"

#### 5. 为什么 `update` 的参数是「目标坐标」，不是直接读 `World`

```ts
update(dt: number, target: { x: number; y: number }): void
```

敌人不知道"玩家"这个概念，它只知道"我要追一个点"。

好处：第 4 步做自动战斗，你可以让 Boss 追小怪；第 6 步做数据表，可以让同一个 `Enemy` 类配不同速度。**谁追谁由外面决定，敌人自己不管。**

这叫**依赖倒置**（听起来吓人，其实就是"别把别人的名字写死在自己身体里"）。

## 第 3 步 · 补 · 碰撞体积（你自己发现的 bug）✅

> 你说：「敌人最后会进入我的方块，这是不是不对，我的方块应该有碰撞体积」。
>
> **对，这是 bug。而且你是自己看出来的，不是我告诉你的 —— 这比做对十道题都值钱。**
>
> 这一步教的是：发现异常 → 说清异常 → 找到原因 → 修掉。这是真实开发 80% 的时间在做的事。

### 目标

敌人贴到你身边就**停住**，不会钻进你的方块里。你跑开，它们继续追；你再停，它们又贴住。

### 概念

#### 1. 什么叫「碰撞体积」

现在你的方块只是一个画出来的矩形。代码里没有任何地方知道「这个方块占地方」——

敌人的逻辑只有一句「朝那个点走」，它走到点上才停。而「那个点」是你的**中心**。

所以三个敌人会一路挤到你的中心，整个人站进你身体里。

**碰撞体积**就是：给每个东西一个"我占多大地方"的概念，移动时不许侵犯别人的地盘。

#### 2. 贴住 = 中心之间隔多远？

两个正方形刚好贴住、不重叠时，中心距是多少？

```
你的方块宽 40，敌人宽 32
你贡献一半（20），它贡献一半（16）
贴住时中心距 = 20 + 16 = 36
```

公式：`(我的 size + 它的 size) / 2`

**记住这个"各出一半"的思路**，后面所有碰撞检测都是它的变体。

#### 3. 两个必须处理的坑（少一个都会出问题）

**坑 1：已经贴住了，还要继续走**

如果只写「走到 36 就停」，敌人到 36 停下；下一帧它算一下距离还是 36，停；再下一帧还是 36……

看起来没问题。但如果它因为浮点误差变成 35.99 呢？那就不满足"到 36 就停"，于是它又走一步，变成 35.5；再下一帧还是 35.5 < 36，继续走……

**结果：它一路挤进去。** 所以判断条件必须是「**小于等于** 36 就停」，不是「等于 36 就停」。

**坑 2：一步跨过头**

现在敌人离你 37 像素，这一帧该走 2.2 像素。走到 34.8 —— **扎进你身体 1.2 像素**。

一帧 1.2 像素你看不出来，但每秒 60 帧，它就会一点点挤进去。

正确做法：这一帧**最多只走到刚好贴住的位置**。也就是：

```
这一帧最多能走的距离 = 当前距离 − 贴住距离 = 37 − 36 = 1 像素
实际走的距离 = min(本来要走的 2.2, 最多能走的 1) = 1
```

`Math.min(a, b)` 取两者中小的那个。这就是**夹取**（clamp），第 2 步夹边界用的是同一招。

#### 4. 为什么 `stopDistance` 由 `World` 传进来

因为敌人**不知道自己在追谁**。它可能追玩家（40）、追另一个敌人（32）、追 Boss（120）。

「该停多远」取决于**对方多大**，而对方多大只有外面知道。

所以 `World` 算好 `(this.size + e.size) / 2` 传进去。敌人只管「离你 stopDistance 就停」，不关心你是谁。

> 这和上一步「为什么参数是目标坐标」是同一条原则：**别把别人的名字写死在自己身体里。**

#### 5. 一个诚实的说明：这个方案有小小的不精确

我们用的是「中心距 36」—— 相当于把两个方块当成**两个圆**来算。

斜着贴上来时，两个**正方形**在这个距离上其实会重叠一点点（实测约 63 平方像素，占方块面积 4%）。

你**看不出来**，游戏也**不在乎**。这是所有游戏都在用的近似（连 3A 游戏也这么干）。

真要精确，得做「轴对齐矩形分离」（AABB），那是第 5 步做血条和攻击判定时的事。现在不需要。

> 学编程要能分清「必须精确」和「差不多就行」。这不是偷懒，这是知道哪里值得花时间。

### 代码

**只改一个地方：`src/core/enemy.ts` 的 `TODO B`（第 90~113 行的注释块）。**

我把 `update` 的签名改了，加了第三个参数（我已经写好，你不用动）：

```ts
update(dt: number, target: { x: number; y: number }, stopDistance = 0): void {
```

`World` 那边也改好了（`world.ts` 的 `update` 里）：

```ts
const stopDistance = (this.size + e.size) / 2;   // 玩家 40 + 敌人 32 → 36
e.update(dt, target, stopDistance);
```

**你要写两处（都在 TODO B 注释块里）：**

```ts
// ① 已经贴住了就别再动（注意是 <=，不是 ==）
if (len <= stopDistance) return;

// ② 别一步跨过头：最多只走到刚好贴住的位置
const step = Math.min(this.speed * dt, len - stopDistance);
```

然后下面两行用 `step`（现在写的是 `this.speed * dt`，要改掉）：

```ts
this.x += (dx / len) * step;
this.y += (dy / len) * step;
```

**顺序很重要：** ① 必须在 ② 前面，② 必须在算位移前面。

### 验证清单

| 检查项 | 正常表现 | 不正常说明什么 |
|---|---|---|
| 站着不动等敌人 | 三个红方块围上来，**贴住就停** | 挤进你身体里 → TODO B 没写 |
| 仔细看贴着的位置 | 红方块边缘和青方块边缘**刚好挨着** | 中间有条缝 → `stopDistance` 算大了（比如用了 40+32） |
| 贴住后再看 5 秒 | **完全不动**，不抖不颤 | 一直轻微抖动 → ① 写成了 `==` 或 `<` 而不是 `<=` |
| 贴住后慢慢挤进去 | 不会 | ② 没写，或写成了 `Math.max` |
| 你跑开 | 敌人立刻跟上来 | 不动了 → ① 写成了直接 `return` 到函数外，或 `stopDistance` 传错 |
| 你停下 | 它们又贴住 | 冲过头 → ② 的 `len - stopDistance` 写反了 |
| 敌人从斜方向来 | 会有一点点重叠，但看得出来是"贴着" | 完全重叠 → 同第一行 |
| F12 → Console | 没有红字 | 有红字，发我 |

### 为什么这么写（后面怎么用）

**为什么不用「碰撞后弹开」？**

那是物理引擎的做法。放置游戏里敌人贴住你是**正常状态**（马上要开始打你了），不需要弹开。

第 4 步自动战斗时，敌人贴住你就是「进入攻击范围」，那时这里会改成「贴住后开始扣血」。

**为什么是 `<=` 不是 `<`？**

`<` 会让「刚好等于 36」这一帧继续走，下一帧就 35.x，然后再也回不到 >= 36 —— 一路挤进去。

`<=` 才是「到了就停」。**边界条件写错一个符号，是新手最常见的 bug 类型之一**，这里正好练一次。

**这套东西后面怎么复用：**

- 第 5 步：血条、攻击判定（`if (距离 < 攻击范围) 扣血`）—— 同一个「算距离、比阈值」的套路
- 第 7 步：掉落物拾取范围（`if (距离 < 30) 捡起来`）
- 第 11 步：Boss 的碰撞体积更大（`stopDistance` 换成 `(40 + 120) / 2 = 80`）

**所以 `stopDistance` 做成参数，不写死 36** —— 你马上就会用到它。

### 最后：一个动手实验

**实验 C：把「夹取」去掉，只留「到了就停」**

把 ② 那行改成：

```ts
const step = this.speed * dt;   // 不夹了
```

**先预测**：敌人会停在 36 吗？还是会挤进去一点？

再去跑。你会看到它们贴上来时**挤进去一点点**（每帧多走 2 像素左右），然后又满足「< 36 就停」，于是停在一个比 36 小的位置。

> 这就是「一步跨过头」的真实后果。你亲眼看见它，以后写任何移动代码都会记得夹一下。

## 怎么打开游戏（三种方式，按省事程度排）

### 方式 1：双击桌面图标「浊仙」（最省事，日常用这个）

桌面上有个青色方块的图标，双击它就行。

它自动干三件事：
1. 检查开发服务器在不在跑
2. 没跑就偷偷起一个（你不会看到黑窗口）
3. 打开浏览器

**第一次双击会慢 4~5 秒**（要编译），之后双击 2 秒内就开。

> 注意：这个图标只在你自己的电脑上有效，因为服务器跑在本机。等第 16 步做完公网部署，才能发网址给别人玩。

### 方式 2：VS Code 里按 Ctrl + ` 开终端，敲 `npm run dev`

适合你要看报错的时候。终端窗口必须开着，**关掉窗口服务器就停了**。

### 方式 3：浏览器收藏夹

服务器开着的时候，直接把 `http://127.0.0.1:5274/` 存成书签，以后点书签。
比方式 2 快，但前提是服务器已经在跑。

## 常见问题

**Q：桌面图标双击没反应 / 浏览器没弹出来？**
先看浏览器地址栏能不能打开 `http://127.0.0.1:5274/`。
- 能打开 → 图标坏了，跟我说，我重建一个。
- 打不开 → 服务器没起来。在 VS Code 终端里手动跑 `npm run dev`，把红字发我。

**Q：怎么关掉服务器？**
正常不用关，它占内存很少。真要关：任务管理器里找 `node.exe`，或者重启电脑。
（不要用 `Ctrl+C` 去关那个你看不到的窗口——它本来就隐藏着。）

**Q：`npm run dev` 报错 `EADDRINUSE`？**
端口 5274 已经被另一个服务器占了（通常是你已经开了一个）。直接用浏览器打开就行，不用再起。
真要换端口，改 `vite.config.ts` 里的 `port`，比如改成 5275。

**Q：改了代码浏览器没反应？**
Vite 的热更新偶尔会失效。在浏览器里按 `Ctrl + Shift + R` 强制刷新。

**Q：终端里一堆看不懂的红字？**
不要自己猜。把终端里最后 10 行完整复制给我。TypeScript 的报错信息其实很准，但格式对新人不友好，我帮你翻译。

**Q：终端报 `EBUSY: resource busy or locked, watch '...tmpdir\...'`？**
这是 Vite 的文件监听和临时文件打架，Windows 上常见。我已在 `vite.config.ts` 里加了 `watch.ignored` 过滤掉，理论上不会再出现。如果又出现了，告诉我。

**Q：我能不能不用 VS Code，用记事本？**
能，但会痛苦十倍。没有语法高亮、没有括号自动配对、没有报错提示。不建议。

**Q：敌人为什么停在离我那么远的地方？看起来没贴住。**
看 `world.ts` 里 `const stopDistance = (this.size + e.size) / 2 + 10;` 那个 `+10`。
它是我给「留一条缝」用的——不留缝的话敌人会严丝合缝贴着你，视觉上分不清边界。
想贴紧就把 `+10` 删掉。这是**你的设计选择**，不是 bug。

**Q：怎么验证我写的东西到底对不对，不用靠眼睛看？**
跑这个（我写的一次性检查脚本，不属于你的学习任务）：

```
node F:\dsh-work\tools\probe-zhuoxian-step3b.mjs
```

它会开一个无头浏览器，自己玩一遍，逐项打印"OK/FAIL + 实测值"。
全 OK 就是对的。有 FAIL 就把整段输出发我。

**Q：`+10` 这种"留余量"的写法常见吗？**
非常常见。碰撞检测里的 `stopDistance`、拾取范围、攻击距离，几乎都会留一点容差。
**但要知道自己为什么留**。随手加的余量和有意留的缝，在代码里长得一模一样，只有写的人清楚。

## 事故记录 A1 · session.ts 被整文件覆盖（2026-10-22 08:33）

- **现象**：`src/core/session.ts`（14.6KB）在 08:33:24 变成 88 字节的一句话，tsc exit 2、6 个测试文件红、两名 teammate 的工具链全部瘫痪。
- **根因**：我写的一次性补丁脚本 `tools/patch-talent-auto.mjs` 里，辅助函数定义成 `function repl(old, neu, tag)`（3 参），调用却写成 `repl(c, old, neu, 'tag')`（4 参）。于是 `old === c`（整个文件内容），`c.replace(c, neu)` 把全文替换成一小段片段。同类错误在 `tools/patch-probe-save.mjs` 已经犯过一次（那次只毁了 `tools/` 下的探针，代价低所以没当回事）。
- **为什么难恢复**：目录不是 git 仓库、没有备份、VS Code 历史里没有这个文件（一直是脚本改的，没在编辑器里打开过）、Vite 已重新 transform 过坏文件、系统 shadow copy 都早于文件创建时间。
- **恢复方式**：按三路证据重建（5 个 import session 的测试文件当可执行契约 + `tools/` 下 20 多个 patch 脚本里残留的 old/new 源码片段 + 全部调用点），重建后 352 测试全绿、探针 25/25 与 26/26 通过、时间线约 400min，与 412.8min 的定稿同量级。
- **代价**：约 40 分钟 + 两名 teammate 阻塞。侥幸没有丢功能（测试覆盖到的地方都在）。

### 由此定下的三条硬规则（所有改源码的脚本必须遵守）

1. **`repl` 统一签名 `(old, neu, tag)`**，第一参永远是被替换的源码片段，绝不允许把整个文件内容当第一参传进去。
2. **写盘前做形状断言**：结果长度 < 原文 × 0.9 直接 throw，不写盘。这次事故的新内容只有原文的 0.6%，一条断言就能拦住。
3. **写盘前留快照**：`tools/_bak/<文件名>.<时间戳>`，至少留最近一份。**没有备份的自动化改写等于没有 undo 键**。

### 顺带发现的一条可测性设计

浮字抖动用 `s.rng.float()` 会让「第几条随机数」整体错位，后续所有掉落序列都跟着变 —— 重建时实测某颗种子满级时长因此偏离 10%。**纯显示的东西不许消耗 RNG**（改成基于伤害值的确定性抖动）。这条对以后加任何特效都适用。

### D42 层 28 硬天花板 → 下潜不再判 hasBossFloor（2026-10-22，ceshi FINDING 1）
- **症状**：6/6 种子卡在层 28，层 29~46 完全不可达，满级后整段挂在层 28 原地刷。
- **根因**：下潜条件写成 `wave % BOSS_EVERY === 0 && hasBossFloor(floor) && floor < MAX_FLOOR`，

  (ii) 最差部位 ≥ 0.85×（放宽单部位门槛，但仍是 min-of-10）；(iii) 维持 10/10 并把窗口上限抬到能容纳最差种子（反对：
  等于把「运气差」写进设计）。若选 (i)，`FORMED_RATIO` 需从 0.80 重推到约 **0.63~0.69**。
- **教训（第 N 次）**：判据必须是**单调量**（上一轮已立），但「单调」还不够 —— 还要看它是**哪个统计量**。
  min-of-N / max-of-N 这类极值统计量对单点运气极度敏感，用它当门禁必须配「允许几个不达标」的容忍度，
  否则门禁自身的抖动就会吞掉真实信号。

### D67 九境目标绑满级（否则门禁永远红）+ 段④ 产出表落地（2026-10-22，ceshi 抓到）
- **真 bug（会让整套门禁变成装饰）**：`tools/run-timeline.mjs` 的 `TARGET_REALM_MINUTES` 末项仍是 **406**
  （D64 之前的满级目标），而 `TARGET_MAX_MINUTES` 已是 **330** ⇒ 第 9 境拿实测 335.0 比 406 = **−17.5%**，
  超 ±15% ⇒ `verdict.pass` 恒 false、**EXIT 恒 1**。谁跑都会以为「数值退步」，其实是目标数组没跟着改。
  ceshi 报上来时把它归因成「满级门禁红」，实际满级那条是 PASS —— 一个漂移的常量能让整块输出说谎。
- **修法（与 D65 同一原则）**：保留**形状**（406 时代的 9 个比例），末项由满级目标推出：
  `REALM_SHAPE = [32,47,70,104,139,179,224,304,406]`、
  `TARGET_REALM_MINUTES = REALM_SHAPE.map(x => round(x / 406 * TARGET_MAX_MINUTES))`，
  并加**启动断言**「末项必须 === TARGET_MAX_MINUTES，否则 throw」。以后重标满级，这条曲线自动缩放，
  不可能再漂；真漂了也会在启动时炸，而不是静默把红盘伪装成绿盘（或反过来）。
- **副作用（已记录，待 shuzhi 判形状）**：等比缩放后第 1 境目标 26min 而实测 **31.6min（+21.6%）→ ✗**，
  第 2 境 +11.7%、第 3 境 +2.9%、第 8 境 +0.5%。即**早期三境偏慢**是老问题（不是这次改出来的），
  等比缩放只是把它显形了。九境行是记录项（不参与 `pass`），但形状该由 shuzhi 重给。
- **段④ 产出表落地（D57/D63 的度量口径终于有数）**：`session-runner` 新增 `postCap` 计数（扫 `s.ground`，
  只统计满级之后落地的仙品，并按 `xueji`/`zhuopo`/`shuangying` 三条旗子拆出「机制传奇」），
  `run-timeline` 新增 **表 2d · 段④ 产出**。实测（3 种子 900min `--post-cap`）：
  **仙品 8.0 件 / 3h**（设计参考 7.2，+11%）、旗子占 **28.6%**（设计 33.3%，样本 ~40 件属噪声）、
  按此 9 件全仙品 ≈ **10 小时**（层 46 口径；层 21 口径约 20h —— shuzhi 的 21h 是层 21 的数，两者不矛盾）。
- **为什么必须把它量出来**：「满级后 512.4min」这类数是假数（窗口 − 满级），跑 1200min 也验不出东西。
  段④ 没有「长度」，只有**产出**：既然满级后修为直接丢弃、层 46 封顶，能回答「满级后还有多少内容」的
  唯一指标就是「一晚上能刷到几件能换的东西」。现在这个数有了，段④ 才第一次可验收。

### D68 段② 判据改 C4（9/10 过线 + 最差 ≥0.70 + 连续 30 分钟不跌破），比值 0.80→0.56（2026-10-22，shuzhi v4.32）
- **背景**：D66 记的「min-of-10 由最倒霉部位决定」被 shuzhi 用**六判据同口径实测**夯实（她自己建探针
  `F:\dsh-work\tmp\criteria-fine.mjs`，3 种子、dt=1/30、无天赋、每分钟采样）：

  | 判据 | 中位(min) | 最差种子(min) | 极差 |
  |---|---:|---:|---:|
  | C0 现行 10/10 | 276.1 | **401.2** | **45%** |
  | C1 纯 9/10 | 187.1 | 190.1 | 1.6% |
  | C2 min ≥0.85（我提的） | 276.1 | 401.2 | 45% |
  | C3 平均≥1.00 且 min≥0.70 | 190.1 | 233.1 | 23% |
  | **C4 9/10 且 min≥0.70（采用）** | **190.1** | **233.1** | **23%** |
  | C5 平均≥1.00 | 49.0 | 80.0 | 63% |

- **为什么否决我提的「最差 ≥0.85」**：读数与现行 10/10 **一字不差** —— 卡住的部位在 **0.49~0.78**，
  把门槛从 1.00 降到 0.85 根本没松开约束。它只能救「差 15%」的种子，救不了「骰烂 50%」的种子。
- **为什么不选纯 9/10**：允许那一个部位**任意烂、甚至空槽**（ratio 0），「9 个部位成型了」这话语义撑不住。
  C4 加下限 0.70，时间几乎不变（190.1 vs 187.1），但挡得住空槽与 0.5 级烂骰。
- **比更换判据更重要的发现（这条才是根因）**：判据 C **不是单调量**。`gearTrail` 的 min 序列在首次达成后
  仍跌破 1~5 次（1.17→1.08→**0.81**→1.54；1.05→**0.70→0.70**→0.92→1.08；1.18→**0.58**→1.12）。
  根因两条：① **D61「带传奇就换」允许低 `itemPower` 的仙品顶掉高战力宝品**；
  ② 换更高灵蕴的件时**分母跟着涨**（`slotBasePower(kind, it.ilvl)` 用该件自己的灵蕴）。
  ⇒ 「首次达成」这个读数取决于当天运气（210 也可能 360），必须定义成
  「**首次满足起连续 30 分钟不跌破，跌破重新计时**」。
- **落地**（`tools/session-runner.mjs`）：`FORMED_MIN_SLOTS = 9`、`FORMED_WORST_FLOOR = 0.7`、
  `FORMED_SUSTAIN_MIN = 30`；采样时算 `passing` 与 `worst`，满足即记 `formedRunSince`，跌破清空；
  `minute - formedRunSince >= 30` 才把 `formedPowerAt = formedRunSince`（**成型时刻取这一段起点**，
  不是确认时刻）。新增诊断字段 `powerChecks / powerChecksOk / powerBestRun`。

- **`run-timeline` 复跑（3 种子 900min `--post-cap`，无天赋 dt=1/30）**：成型 **193.9 / 254.6 / 148.3**，
